## Общие правила работы

- Перед изменениями изучи существующую структуру, похожие реализации и принятые в проекте соглашения.
- Вноси минимальные изменения, необходимые для решения задачи. Не переписывай несвязанный код без явной причины.
- Не дублируй код, типы, константы, стили и бизнес-логику. Сначала найди существующую реализацию и переиспользуй или аккуратно расширь её.
- Сохраняй обратную совместимость, если задача явно не требует изменения контракта.
- Не добавляй новые библиотеки, пока задачу можно решить средствами текущего стека.
- Не оставляй закомментированный код, временные логи, неиспользуемые импорты и заглушки без пояснения.
- Не изменяй секреты и не добавляй содержимое `.env` в репозиторий. Новые переменные документируй только в `.env.example`.
- После изменений запускай релевантные проверки и сообщай, что именно было проверено.

## Frontend

Frontend находится в `frontend/` и использует React, TypeScript, Vite, MUI, React Query, React Hook Form, Zod и Zustand.

### Архитектура

Соблюдай текущие границы модулей:

- `app/` — инициализация приложения, провайдеры, роутинг и глобальная конфигурация;
- `pages/` — композиция страницы из готовых компонентов и feature-блоков;
- `widgets/` — крупные самостоятельные части интерфейса и layout-композиции;
- `features/<feature>/` — бизнес-функциональность, разделённая на `api`, `model`, `lib`, `ui`;
- `shared/ui/` — универсальные компоненты без привязки к конкретной бизнес-сущности;
- `shared/lib/`, `shared/api/`, `shared/config/` — общие утилиты, API-инфраструктура и конфигурация.

Не помещай бизнес-логику в `shared`. Не импортируй страницы в features и shared-модули. Предпочитай зависимости в направлении `app/pages -> widgets/features -> shared`.

### Переиспользуемые компоненты

Перед созданием нового компонента:

1. Проверь `shared/ui`, UI текущей feature и похожие экраны.
2. Если компонент не зависит от бизнес-сущности и может использоваться в нескольких features, размести его в `shared/ui`.
3. Если компонент переиспользуется только внутри одной бизнес-области, оставь его в `features/<feature>/ui`.
4. Если различия между существующим и новым UI небольшие, расширь компонент через типизированные props, `children`, slots или композицию вместо копирования.

Компоненты должны:

- иметь одну понятную ответственность;
- получать данные и обработчики через типизированные props;
- не содержать скрытых зависимостей от конкретной страницы;
- поддерживать композицию вместо множества узкоспециализированных boolean-props;
- использовать MUI и тему приложения вместо самодельных аналогов базовых элементов;
- использовать theme tokens (`palette`, `spacing`, `typography`, `breakpoints`), а не повторяющиеся магические значения;
- корректно отображать состояния loading, error, empty и disabled, когда они применимы;
- быть доступными: семантическая разметка, label для полей, keyboard navigation, видимый focus, `aria-*` там, где семантики HTML недостаточно.

Не создавай общий компонент заранее «на будущее». Выноси абстракцию, когда она уже выражает стабильный повторяющийся паттерн. Если две реализации похожи визуально, но имеют разное поведение, сначала оцени, действительно ли им нужна общая абстракция.

### React и состояние

- Используй функциональные компоненты и hooks.
- Не храни вычисляемые значения в state; вычисляй их из исходных данных.
- Локальное UI-состояние оставляй локальным. Zustand используй только для действительно общего клиентского состояния.
- Серверное состояние, загрузку, кэширование и инвалидацию веди через React Query.
- API-вызовы размещай в `api` соответствующей feature или в общей API-инфраструктуре, но не прямо в UI-компонентах.
- Формы реализуй через React Hook Form, а валидацию — через Zod и общую схему для формы и типов, где это возможно.
- Побочные эффекты используй только для синхронизации с внешними системами. Не применяй `useEffect` для обычных вычислений или обработки событий.
- Не выполняй преждевременную мемоизацию. Добавляй `useMemo` и `useCallback`, только когда есть измеримая причина или это требуется контрактом зависимости.

### TypeScript

- Не используй `any`. Для неизвестных данных применяй `unknown` и выполняй проверку/сужение типа.
- Не дублируй доменные типы. Храни их в `model/types.ts` соответствующей feature.
- Явно типизируй публичные props, API-контракты и возвращаемые значения общих утилит.
- Обрабатывай `null` и `undefined` осознанно; не скрывай проблему необоснованным non-null assertion (`!`).
- Используй понятные предметные имена. Избегай сокращений, смысл которых не очевиден из контекста.

### Стили и адаптивность

- Следуй существующему подходу MUI (`sx`, theme, styled components); не смешивай несколько способов стилизации без необходимости.
- Не копируй крупные объекты `sx`. Повторяющиеся визуальные паттерны выноси в компонент или общую стилевую функцию.
- Интерфейс должен работать как минимум на мобильной и desktop-ширине.
- Не фиксируй размеры, если контент может безопасно определять их сам.
- Избегай inline-цветов и значений, которые уже представлены токенами темы.

### Качество интерфейса

- Текст кнопки должен описывать действие, а заголовок — результат или содержание экрана.
- Опасные необратимые действия должны требовать подтверждения.
- Ошибки должны быть понятны пользователю и не раскрывать внутренние детали API.
- Не допускай скачков layout при загрузке, двойной отправки форм и повторных запросов из-за неконтролируемых эффектов.
- Сохраняй единообразие отступов, размеров, терминологии и поведения с существующими экранами.

## Backend и API-контракты

- Не меняй API-контракт без проверки всех его потребителей.
- Валидация на frontend улучшает UX, но не заменяет backend-валидацию.
- Обрабатывай ошибки единообразно через существующие API-утилиты.
- Не показывай пользователю сырые stack trace, SQL-ошибки и внутренние сообщения сервера.
- Миграции должны быть последовательными и безопасными для уже существующих данных.

## Проверки перед завершением задачи

Для изменений frontend выполни из `frontend/`:

```bash
npm run lint
npm run build
```

Также проверь вручную или тестами:

- основной пользовательский сценарий;
- loading, error и empty states;
- валидацию и защиту от повторной отправки форм;
- мобильную и desktop-компоновку;
- отсутствие ошибок и предупреждений в консоли;
- доступность изменённых интерактивных элементов с клавиатуры.

Если проверку невозможно выполнить, явно укажи причину. Не утверждай, что задача полностью проверена, если соответствующие команды не запускались или завершились ошибкой.

## Критерии готовности

Задача готова, когда:

- реализовано запрошенное поведение без несвязанных изменений;
- существующие переиспользуемые компоненты использованы или расширены вместо копирования;
- новые общие компоненты находятся на правильном архитектурном уровне;
- учтены основные состояния интерфейса и доступность;
- код типизирован, читаем и соответствует форматированию проекта;
- релевантные lint/build/tests проходят;
- итоговое сообщение кратко перечисляет изменения, проверки и известные ограничения.
